## Add — research, review and save a restaurant

- [x] Discover → choose a branch → research → preview → owner-confirmed publication is implemented. Session versions, duplicate-safe replay, location validation, source evidence and public catalog readback are covered by tests and live Add journeys. A failed lookup cannot silently publish an unlocated restaurant.
- [x] If research leaves fields unknown, the owner can correct details and refresh the preview; an address or coordinates are still required for publication. The separate Review tab and candidate publication path have been retired; historical schema and receipts remain readable.
- [x] Saved-place duplicate checks use provider/listing identity and corroborated location across Japanese, Chinese and English names. Strong matches open the existing item and block another publication; same-building uncertainty remains a warning. Controlled and deployed cases cover this path.
- [x] Source readers validate branch identity, aggregate ratings, cuisine, dishes, reservation rules and booking links. Unsupported or failed sources remain unknown. Tabelog listing IDs of current lengths, unrated listings, selected chains, aliases, numeric branch spellings and wrong-branch negatives have regressions.
- [x] Presentation uses a concise Chinese overview grounded in validated cuisine, area and up to three distinct dishes. Top tags retain at most two distinct categories and two dishes; overlapping category names are collapsed. Controlled cases and repeated live previews cover the named regression set.
- [x] Japanese ratings favor Tabelog, eligible overseas restaurants can show Google review scores, and mainland China does not require a Google score. Personal rating remains separate. Source citations and aggregate-score checks reject review-level scores.
- [x] The Add evaluation set includes selected-place, chain, spelling, regional-source, manual-completion, duplicate, presentation, reservation, and official-site failure/recovery cases. The current controlled Add behavior suite passed 112/112; a deployed DeepSeek discover-to-preview set passed its nine named cases. Candidate-only discovery passed 40/40 and live aggregate-rating completion passed 4/4. These finite sets do not prove universal source availability.
- [x] Owner model settings, encrypted server-side credentials, no-key search fallback and bounded source readers are implemented. The model proposes facts; the application validates them and controls writes. Provider blocks and challenges surface as incomplete research, with owner completion available.
- [x] Deployed Add previews and publication have shown refreshed catalog visibility, location, branch-specific rating, reservation details and duplicate detection. The reported failure for a numeric-branch restaurant was not retained in a production trace; its exact stage remains unproven. The branch-spelling robustness fix and negative controls are implemented.
- [ ] Measure ongoing live source reliability and broader branch disambiguation beyond the named set. Unsupported menu details and booking lead times must remain unknown.

Map search filters visible rows and markers by name or alternate title. Journal ordering supports visit date and entry time in both directions with stable ties.

## Recommend — suggestions from saved restaurants

- [x] The deterministic foundation reads verified saved food only, uses catalog/route evidence, prefers unvisited places and provides exact saved-detail targets. The final receipt rereads current D1 identity and source facts, rejects removed/changed/mismatched candidates, and emits the database's canonical name and address rather than a model-generated one.
- [x] The owner-authenticated, no-store Recommend API accepts a bounded query, replies and optional verified origin choice. The Map UI supports follow-up questions, keyboard answers, geocoder choices, reset and retry without losing the draft. Broad-area requests can return area matches; timed route requests require an exact origin. A pasted shop name or map address can be an origin hint.
- [x] Without an explicit travel mode, a precise origin ranks saved restaurants within 2 km straight-line distance and labels travel time unverified; a broad area carries no distance or time claim. “Near me” asks for a start. Explicit walking keeps fresh route/time checks; explicit driving truthfully reports unsupported. Walk-in entry wording is distinct from walking duration, and sourced booking rules can exclude incompatible recommendations while unknown availability stays unknown.
- [x] The private Route Sidecar batches walking destinations. Existing direct-rail support is optional and unavailable for Japan through Google Routes; it is outside the PoC release benchmark and requires no paid alternate provider or extra credential.
- [x] The frozen model-only benchmark has 34 intent, 8 dialogue, 26 decision, 14 retained Nearby policy and 10 station cases (92 total). Three original DeepSeek baseline runs passed 27/92, 28/92 and 27/92. Three fresh production-interpreter runs passed the 34+8 intent/dialogue cases each time; an additional paraphrase regression passed 15+4 after a near-me fix. These runs use synthetic options and do not establish browser acceptance.
- [x] Current deterministic extensions cover default distance, proximity intent, walk-in entry and wording, plus 14 application contracts. Current release fixtures require straight-line distance with an uncertainty warning by default, and sourced walking time only when explicitly requested; they contain no train-time acceptance case. The application scorer also rejects a displayed invented duration or any transit route claim. The frozen 92-case historical baseline remains available for comparison, with its old transit scenarios excluded from the current release rate. Scorers and oracle tests distinguish action, saved identity, route/source safety, clarification and UI continuation.
- [x] Deployed browser subsets verified broad-area suggestions, exact-origin replies and choices, direct saved-detail clicks, distance caveats, a sourced walking route, draft-preserving retry, walk-in uncertainty, English station names and pasted addresses. After the latest deployment, a default-distance request returned saved matches with straight-line distances and an unverified-time warning; an explicit ten-minute walking request returned a canonical saved match with a verified provider route and citation. These are partial acceptance results.
- [ ] Capture and score all 14 owner-authenticated browser/API application traces, including default-distance and explicit-walking behavior, provider failure and mobile continuation. Oracle tests and partial browser checks do not close this gate.
- [ ] Add image-based location understanding only after collecting labelled screenshot cases and a separate modality baseline.
