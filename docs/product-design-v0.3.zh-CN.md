# Japan Atlas 产品设计 v0.3

状态：有效产品基线
最后更新：2026-09-07
取代：`product-design-v0.2.md`

## 1. 产品定义

Japan Atlas 是 Andy 私有、长期使用的餐厅、咖啡店、活动、展览和建筑地图。它不是通用旅行规划器，也不是以网页数据录入为主要目标的产品。

产品包含两个相互补充的界面：

- **微信 Agent——主要操作入口。** 接收链接、创作者、文字、语音、位置、照片和到访备注；询问附近推荐；更新记录；接收进度或澄清问题。
- **私有地图——主要浏览与记忆入口。** 按空间探索收藏，查看来源与预约事实，浏览个人照片与到访历史，对比去过／没去过地点，并进行偶尔的修正。

两个入口都调用同一套产品操作并使用同一份持久化数据。地图绝不能成为第二个相互冲突的数据库。

## 2. 交互边界

### 以 Agent 为先的操作

- 将创作者／主页／帖子加入采集队列；
- 从文字、语音、位置或图片新增一次 Visit；
- 关联照片并添加说明文字；
- 设置或更新一个地点唯一、持久的个人评分；
- 查询附近、没去过、当前营业或满足预约条件的地点；
- 编辑地点文字与个人元数据；
- 接收导入进度，并回答简短的澄清问题。

### 以地图为先的操作

- 浏览与搜索可信集合；
- 查看地图标记与选中地点详情；
- 查看来源链接、带日期的评分、预约信息、活动日期与信息新鲜度；
- 每个地点查看一份统一的个人记录；
- 浏览各次 Visit 与照片，而不复制地点；
- 按去过／没去过、已收藏／已计划、类型、区域、标签与时间敏感状态筛选；
- 通过网页进行偶尔的修正或上传，作为备用入口而非日常主要流程。

### 过渡期导航

当前独立的 Inbox 与 Journal 页面会暂时保留，直到微信写入路径达成功能一致。它们不应决定最终信息架构。目标地图使用上下文面板：

- 选中地点的 **My record** 面板，用于评分、Visit 与照片；
- 当地点身份存在歧义时，从微信打开审核深链接；
- 在替代流程稳定后，不再保留永久的 Inbox 或 Journal 一级入口。

这样可以避免在 Agent 可用前，过早删除目前唯一能工作的写入界面。

## 3. Journal 与个人记忆模型

当前模型错误地为每条 Journal 记录存储一个评分。替代模型把地点级评价与可重复的 Visit 分离。

### `PlaceAssessment`——每个 Atlas 条目一份

- `itemId`——与地点／活动／建筑的唯一关联；
- `overallRating`——可选、可空；存在时为任意有限的 0–5 数值；
- `summary`——可选的长期看法；
- `collectionState`——candidate、saved、planned 或 archived；
- `updatedAt`。

每个条目始终只有一个当前个人评分。后来修改评分会替换该值，同时由审计日志记录变更。参观美术馆可以完全不评分；`null` 表示“未评分”，而 `0` 是有效的明确评分。直接数值输入接受 0–5 的任意数值。未来的滑条或快捷评分控件可以 0.5 递增，但不能因此限制手动输入精度。

### `Visit`——每个 Atlas 条目可有多条

- `id`、`itemId`、`visitedAt`，以及可选备注；
- 到访序号根据同一条目的 Visit 按时间推导；
- 未来可增加可选的同行人或上下文结构；
- 创建／更新时间戳。

“去过”由至少一条 Visit 的存在推导。UI 显示“第 1 次／第 2 次／第 3 次到访”，但不要求用户手动维护计数器。一次 Visit 必须至少包含一种记忆内容：评分、笔记或图片。因此，“只有评分、没有图片和笔记”是有效记录；三者皆空则无效。在媒体上传功能上线前，网页／API 备用入口至少要求评分或笔记之一。

### `MediaAsset` 与 `VisitMedia`

- 图片二进制存放在 R2 兼容对象存储；
- D1 存储对象 key、MIME 类型、尺寸、哈希、上传状态、时间戳和归属关系；
- 每张图片可以有一行可选说明，例如菜品、房间、建筑立面或展区名称；
- 媒体可以关联到 Visit，并可由此定位到其 Atlas 条目；
- 展示顺序必须显式保存，并尽可能按内容哈希去重。

Agent 与网页备用入口使用同一套上传生命周期：创建上传意图、存储二进制、完成元数据、关联／添加说明，然后显示在地图详情中。

## 4. 地图展示

选择地图标记或搜索结果后，打开一份统一的地点记录：

1. 日文优先名称、类型、地址、标签与去过／没去过标识；
2. 并排显示个人评分与食べログ／Google 评分，便于直接比较；
3. 官网与预约信息，并在底部统一显示一次最新核验日期，而不是在每项事实旁重复时间戳；
4. Visit 次数、最近到访日期与按时间排列的到访记录；
5. 按 Visit 分组的照片条，每张图片显示其说明；
6. 个人总结与有来源依据的地点描述。

重复到访只会扩展时间线；它们绝不会创建重复地点卡片，也不会争抢同一个固定高度面板。列表应使用自然内容高度或稳定的滚动区域，而不是把固定高度平均分配给所有条目。

地图标记样式与筛选项需要区分：

- 没去过的候选地点；
- 去过的地点；
- 已计划／已收藏地点；
- 时间敏感的活动与预约放号。

推荐默认优先没去过的地点，除非 Andy 明确要求喜欢、重访或全部结果。

喜欢与去过状态在选中地点详情和可折叠集合中都使用纯图标的心形与圆圈／勾选控件。它们采用乐观更新并与持久 API 对账，因此正常网络延迟不会阻塞可见反馈。

当仅个人状态变化时，地图必须复用现有标记；地图移动期间应避免使用全画布 filter 或 blur 效果。实验阶段可以接受 OSM 栅格地图作为基线；如果达到 Google Maps 级别的移动体验仍是产品要求，则另行评估矢量地图服务商。

## 5. 搜索与发现

搜索分为两层：

### 确定性网页搜索

在本地对规范化后的日文、中文和英文文本运行，并支持：

- 标题部分匹配与拼写容错；
- 别名、区域、地址和描述；
- 可见标签与别名；
- 多词查询分词；
- 去过／没去过及其他结构化筛选。

标签搜索不需要 LLM。结果卡与详情卡上应显示标签，使搜索行为可被用户检查。

### Agent 语义搜索

Agent 将“附近没去过、可以 walk in、安静一点的咖啡店”等请求转换为结构化筛选、语义意图与排序。它可以解释结果为何匹配，但不得编造标签或事实条件。来源与新鲜度规则仍然适用。

## 6. Agent 操作契约 v2

必需操作：

- 带去过状态和距离筛选的 `search_atlas` 与 `recommend_places`；
- `get_item_details` 与 `get_visit_history`；
- `create_visit`，备注可选且不强制评分；
- 将 `set_personal_rating` 作为地点级 upsert；
- `attach_visit_media` 与 `caption_media`；
- `update_atlas_item` 与 `update_tags`；
- `queue_creator_import`、`get_import_status` 及 review candidate 相关操作。

每次写入都需要幂等键、类型化验证、审计事件与人类可读回执。OpenClaw 等渠道适配器将消息映射到这些操作，但绝不直接写入 D1 或对象存储。

## 7. 数据与信任规则

1. 生产集合中不得存在未标注的 demo 数据。
2. 精确地点／分店身份必须有证据支持，否则保持待审核状态。
3. 默认显示日文标题；保留日文、中文与英文来源文本，不强制翻译。
4. 外部评分与 Andy 的可选个人评分必须分离。
5. 预约与活动事实保留来源和核验时间；“最早可预约时间”只能根据已发布规则或实时日历计算。
6. Journal 图片与备注属于私有产品数据，绝不作为公开作品集的示例数据。
7. 删除 Visit 或图片时应尽可能可恢复，且不得因此删除其规范地点。

## 8. 当前状态

项目处于**实验阶段**。持久化地图与 API 真实可用，但主要 Agent／微信工作流、采集 worker、媒体存储与替代 Journal 模型尚未全部完成。当前 Inbox 与 Journal 是过渡脚手架，不是最终产品导航。
