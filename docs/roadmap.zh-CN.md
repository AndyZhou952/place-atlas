# 产品开发 Roadmap v0.3

状态：有效
最后更新：2026-09-07

产品目前处于**实验阶段**。数据库、私有地图、带来源记录和 API 都是真实可用的；预期的日常 Agent 渠道、媒体链路、创作者采集器和统一地点记忆尚未完成。各任务状态和依赖关系见 `task-tracker.zh-CN.md`。

## 已完成 — 持久化基础

- 私有 GitHub 仓库与仅所有者可访问的托管地图；
- 已审查旧原型，但没有把它作为新代码基线；
- 经来源核验的真实记录，默认显示日文标题；
- 带日期的食べログ／预约事实、官网链接与活动日期；
- 编辑、导入任务与第一版到访原型使用 D1 持久化；
- HTTP 与浏览器 Agent 共享操作；
- 已安装 Web Access，用于独立浏览器实验；
- 渠道、Agent、产品核心和采集层之间已有架构分离；
- 每个地点一个持久、可选的个人评分，以及可重复且无需评分的 Visit；
- 持久化喜欢／去过状态、带确认边界的破坏性地点删除，以及内置记录的 tombstone；
- 交互式多标记地图、可折叠地点抽屉、可见标签、确定性部分／标签搜索；
- 浏览器 Agent 通过与网页 UI 相同的 API 提供偏好、评分、Visit 与删除工具。
- 详情和可折叠集合中均使用纯图标喜欢／去过控件，并提供即时乐观反馈及失败回滚；
- 复用地图标记并减轻地图合成负担，显著加快平移、缩放、选择和个人状态变化；
- 一个主构建和一个数据库提供实时 A／B／C 展示 URL；
- 个人评分与食べログ评分并排比较，并在地点详情底部统一显示一次来源核验日期。
- 分栏侧边栏（B）已选为主版本默认布局；
- 详情与集合列表并列显示 `マイスコア` 和食べログ，并通过 ViewModel 支持双击编辑；
- 到访／喜欢筛选可组合并按交集显示，到访控件固定显示 `行った`；
- Journal 新增／修改／删除均采用即时乐观交互；约两秒的托管回包在后台完成并记录在 issue #2，地图分析记录在 issue #1。
- Journal 支持 Visit 编辑、确认删除，以及按地点／日期范围筛选回忆；
- 上下按钮按 0.5 递增，同时允许输入任意 0–5 数值并规范化到一位小数；
- 地图已隔离为可替换的 Leaflet 适配器，恢复渐进瓦片调度并按 key 对账标记；
- Visit 使用幂等 ID；Journal 写入合并为原子批次，写入路径不再全表读取。

## 阶段 1 — 修正个人记忆模型

目标：无论重复到访多少次，一个地点始终只保留一个地点身份。

- 完成 Journal 纠错与空状态的托管验证；
- 明确 `hasVisited` 推导与人工覆盖的语义；
- 为个人写入添加幂等与审计记录；
- 将选定的分栏布局重构为职责单一的视图组件；
- 使用别名与经过测试的排序夹具扩展确定性模糊搜索。

退出条件：一个美术馆可以有三次 Visit、零或一个总体评分，且所有备注都集中在一个地点详情中，不出现重复地点卡片。

## 阶段 2 — 照片与说明文字

目标：让个人视觉记忆可以持久保存并在地图中查看。

- 配置 R2 兼容对象存储；
- 添加媒体元数据、上传状态、Visit 关联、排序与内容哈希；
- 接受常见手机图片格式，并校验大小／类型；
- 允许每张图片附带可选的一行说明；
- 在地图详情中按 Visit 展示缩略图与图库；
- 网页上传作为备用方式，Agent 上传作为主要路径。

当前进度：私有 R2、D1 元数据、签名／大小／哈希校验、每次 Visit 多图上传、单行说明编辑／删除及地图详情展示已经完成。服务端图片尺寸解析与定时孤儿对象清理完成后，本阶段才正式关闭。

退出条件：从任一支持入口发送的图片，刷新后都能在正确地点与 Visit 下显示，并保留说明文字。

## 阶段 3 — Agent 应用层

目标：让微信无需直接访问数据库即可操作产品。

- 从当前 store 中抽取与框架无关的 use cases；
- 添加搜索／推荐、Visit、持久评分、标签和媒体的类型化操作；
- 要求服务鉴权、幂等、权限控制与审计事件；
- 将自然语言转换为结构化筛选，同时保留来源；
- 附近推荐默认优先没去过的地点，除非用户明确提出其他要求。

退出条件：非微信测试适配器可以执行全部日常流程，且地图立即更新。

## 阶段 4 — 独立浏览器采集实验

目标：在批量导入前，证明按创作者采集的流程可用。

1. 使用独立 Chrome／Edge profile 和社交平台小号；
2. 对“在日本摸鱼的小超人”运行一小批发现任务；
3. 持久化帖子元数据与证据，而不是只保存最终猜测；
4. 增加正文／评论、ASR、抽样关键帧和多语言 OCR；
5. 使用来源解析精确分店，将不确定项送入审核；
6. 冒烟闭环可用后，再对约定的创作者集合进行校准。

退出条件：一个创作者引用至少产生十条可审核帖子；局部失败保持可见；在允许放弃判断的前提下，自动确认结果的精确分店准确率达到至少 90%。

## 阶段 5 — OpenClaw 与微信

目标：让 Andy 的微信私聊成为主要输入与指令入口。

- 验证主账号私聊的文本、图片、语音、链接和位置流程；
- 把消息映射到测试适配器所使用的同一套 Agent 操作；
- 返回即时回执与异步进度；
- 对模糊的视觉审核提供指向相应地图上下文的深链接；
- 测试重试、重复投递、重启及连续七天可靠性；
- 仅在功能对等后移除永久 Inbox／Journal 导航。

退出条件：日常采集、附近未去过地点推荐、编辑、Visit、照片和导入请求都能从微信发起并显示在地图上。

只有消息往返验证成功后才应租用 24/7 服务器。初步按 2 vCPU、4 GB RAM、加密存储和每日备份规划；根据实测延迟与运维可靠性选择区域。

## 阶段 6 — 产品成型与交付

- 预约／活动新鲜度与 JST 提醒；
- 手机优先布局与容忍离线的最后一次同步数据；
- 备份／恢复演练；
- 一周纯手机旅行演练；
- 安全与成本审查；
- 为日后作品集准备已清理私密信息的架构／demo 材料。

退出条件：个人产品足够可靠，可在日本旅居期间使用。通用化明确放在 v1 之后，且绝不暴露 Andy 的私有来源、照片或 Journal。
