# Agent Add 体验与稳定建档规格评审 (第 1 轮)
- 日期: 2026-09-24
- 评审方式: subagent
- 结论: 需修改
## 发现项
- [严重] `Solution` 5、`Acceptance Criteria` 15 及 `Implementation Decisions` 78: 规格把 `WebResearchPort` 称为“已审核”并纳入交付，却没有承接上游架构中仍为 Proposed 的 D-P06 生产信任区门；现有 feature 005 明确要求真实 Relay 在签名 allowance、Tunnel 身份、双栈 DNS/IP pin、redirect/rebinding、单次 egress 和公网旁路负测通过前保持 disabled。当前验收标准可在未闭合这些门的情况下被判定“Research 已完成”。 → 明确区分“已评审的 port/fixture contract”与“未批准的 production Relay”；将 D-P06 的 preflight、负向 probes、fail-closed/rollback 和真实单店 smoke 写成必过验收项，否则本特性只能交付 manual/unknown 退化路径。
- [一般] `Acceptance Criteria` 11–12 与 `Testing Decisions` 84: 新增的 Google transient location 交叉核验没有可判定的阈值、边界语义或唯一结果；“经批准的距离阈值”未给出值或决策工件，而“conflict／needs review 且零发布”同时允许了两种业务结果。此外，规格未将新增 transient 坐标纳入 D1/R2/log/prompt/receipt/Leaflet 零持久化的负测。 → 固定阈值、边界是 `<=` 还是 `<`、超阈值时的单一闭合 outcome 与二次确认方式，并明确 Google 坐标仅存在于当次 provider 调用内的负面存储清单。
- [一般] `Acceptance Criteria` 13–14 与 `Testing Decisions` 85: `SemanticAddProposal { action:'add', query, clarification? }` 尚不是可实现、可测的闭合契约；`clarification` 的类型/长度/允许字段未定义，也没有规定哪些自然语言输入进模型、proposal 成功后如何确定性地映射到 `catalog.intake.discover`、追问回答如何续上原 session，以及模型失败时用户得到什么可操作回复。 → 给出版本化 JSON Schema 的完整字段、bounds 和 closed-union，写明 `message → proposal/clarification → discover` 状态转移、会话绑定、回退文案及不会自动 select/confirm 的负面验收。
- [一般] `Solution` 6、`User Stories` 10、`Acceptance Criteria` 18 及 `Further Notes` 101: 类别、推荐菜和 Owner 备注既被列为本特性方案/验收，又标成“另行扩展”和 deferred，无法判断何时算本 feature 完成。“Owner 备注”也未在 `CONTEXT.md` 定义其属于公开 Catalog 事实、私人 Personal Memory 还是 Visit 内容，缺少可见性、更新和投影语义。 → 要么把它们移到明确命名的 follow-up feature/Out of Scope；要么先补共享语言与公开/私有边界，再为 schema、migration、Web/Agent 读写、投影和回滚分别给出可测验收标准。
- [一般] `Acceptance Criteria` 17 以及整个规格的 UI 决策: 特性要修改 Web Owner Add 表单和微信可见呈现，但没有按 UI 规格门说明复用 warm editorial atlas 设计系统、taste 参数与令牌，也没有覆盖 Web 新增 Tabelog/预约编辑的 loading、empty、invalid/error、disabled、success 和 focus 行为、字段验证及可访问错误关联。 → 增加 UI Design 节并显式继承 feature 005 的美学方向、`3/1/3` taste 和现有 token；将 Web 编辑与微信 presenter 的主态/失败态、键盘/焦点、ARIA 以及移动真实渲染验收写成可判定条件。
- [一般] `Acceptance Criteria` 5、7 与 `Testing Decisions` 83: “目标不超过 900”和“必要的下一步”是不可判定的模糊量词，而截图中的核心问题正是手机文案密度与换行。 → 把 900 code points 改为必过上限（或按 normal/warning 分别定义硬上限），并为 `committed_verified | committed_needs_review | reused_existing`各给出精确字段、行序与允许的 CTA，使 presenter contract 可以稳定断言。
