# 004 OpenClaw × Japan Atlas PoC 架构评审

- 日期: 2026-09-13
- 评审方式: subagent
- 结论: 需修改（FAIL）

## 发现项

### 严重

- [严重] `architecture.md:17,29,37`：`PreModelIngressRouter` 在 Lightsail，权威 capture session 却保存在 Cloudflare D1；架构没有定义 router 如何在重启、状态刚切换或网络分区时取得 owner/channel/conversation 对应的当前 session/state/version。仅凭本机内存会在重启后遗失 active capture，盲目远端查询失败后若落入“普通聊天”，又可能把本应进入私人草稿的文字／图片交给模型，破坏确定性路由和隐私边界。→ 增加窄而权威的 `CaptureRouteLookup` 接缝：在任何可能进入模型的普通文字／图片前，以签名请求取得绑定 actor/channel/conversation 的 session ID、state、version 与短有效期；允许缓存时必须使用服务端签名断言并在状态转移后失效。查不到可以进入普通助手，结果 stale／超时／不确定时必须固定失败关闭，不进模型、不改草稿，并提示重试。把 gateway/ingress 重启、状态切换竞态、缓存过期和网络分区加入真实链路测试。
- [严重] `architecture.md:20,24,32,39,53` 与现有 `apps/web/product/application/visits/visit-operations.ts`、`apps/web/product/application/media/media-operations.ts`：架构声称能完成“D1 原子业务提交与 R2 staged publish”，但没有定义一个拥有该不变量的 Application Operation／port。当前 `visit.create` 只原子写 Visit＋可选 assessment，`media.attach` 则先写正式 R2 key、再单独写媒体元数据；`AtlasConversationCoordinator` 又被禁止直接访问 D1/R2。若 coordinator 顺序调用这些旧 operation，不可能让 Visit、assessment、全部媒体元数据和最终 receipt 通过一次 D1 transaction 同时可见，也无法实现 `recovery_required → committed | abandoned`、response-lost 回执重放和 24 小时 orphan reconciliation。→ 在 Application Operations／Personal Memory 内定义单一深接缝（例如 `VisitCapturePublisher.publish(confirmedPreview, mutationId)`），其后方由一个 composite D1 state port 在同一 transactional `batch()` 中校验 mutation digest/preview version、插入或发布 Visit＋assessment＋全部 media metadata、更新 capture 状态并保存最终 receipt；R2 port 明确提供幂等 stage/promote/verify/delete，使用稳定 object IDs，所有对象经 size/hash 核验完成后才允许 D1 publish。列出每个故障点、可见性、重试与 abandon/reconcile 结果，并说明 R2 promote 采用 Workers get/put 还是受限的 S3 `CopyObject`，不得把 R2 操作描述成 D1 事务的一部分。[D1 `batch()` 的事务保证](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)、[R2 S3 `CopyObject` 支持边界](https://developers.cloudflare.com/r2/api/s3/api/)。
- [严重] `architecture.md:54` 与 `spec.md:142,182`：架构允许 DeepSeek 接收“降质媒体”，而已通过的规格明确规定图片二进制不进入模型 prompt，并把发送图片给 DeepSeek列为范围外。这会把未经批准的私人 Visit 图片送入云模型，属于直接的隐私边界回退。→ 删除“降质媒体”；本特性只允许 DeepSeek 接收批准的文字和最小附件元数据，且不得含图片 bytes、可还原缩略图或 EXIF。未来若需要视觉理解，必须另立规格、模型保留/训练条款和隐私评审。

### 一般

- [一般] `architecture.md:15-25` 与 `spec.md:153-159`：一个 `AtlasConversationCoordinator.handle(channelEvent)` 同时隐藏 Catalog intake、Visit capture、附件暂存、预览、确认、恢复和幂等，接口过浅而内部跨越 Atlas Catalog、Personal Memory 与两套独立 session；同时规格要求的 `CatalogIntakeCoordinator.handle` 与 `ConversationCoordinator.handle` 两个高层测试缝在架构中被合并，Catalog 对 strong identity、疑似重复、immutable evidence、catalog revision、verified/abstain 和单事务 receipt 的所有权没有落点。→ 保留可选的 channel façade，但在其后明确两个深模块：`CatalogIntakeCoordinator` 只编排 discovery/evidence/preview 并调用 Atlas Catalog 独占的 `catalog.intake.confirm` operation；`VisitCaptureCoordinator` 只管理 capture/attachment/state table 并调用上述 capture publish operation。补一张无环依赖图和与规格五个测试缝的一一映射，禁止 coordinator 绕过 `AtlasApplication` 或自行决定 verified。
- [一般] `architecture.md:18-19,24,30` 与现有 `apps/web/features/atlas/atlas-browser-operation-catalog.ts`：规格要求版本化、闭合且按 Read-only／Write gate 投影的 Agent tool manifest，但架构没有为它指定 owner 或与现有 browser capabilities 的边界。现有 browser catalog 会公开 update/delete/media-delete 等能力，直接复用会违反第一阶段只有 nearby read scope、第二阶段仍不开放 destructive 的要求。→ 定义唯一 `AgentToolCatalog` 投影：从静态 Application Operation descriptors 加上 Agent 专用 schema/effect/scope/confirmation/retry metadata 生成，按 project＋phase allowlist 过滤，默认拒绝 destructive、maintenance、reset 和底层 `catalog.save_discovered`；不要复制业务 handler，也不要复用当前 browser capability 清单作为授权来源。对 manifest 快照、阶段切换和“隐藏 key 无法直接调用”做 contract tests。
- [一般] `architecture.md:29,39,52`：HMAC 虽覆盖 method/path/body digest/timestamp/nonce/key ID，但协议仍不足以同时满足防重放与 mutation/receipt 重试。没有定义 canonical path/query/body bytes、nonce 唯一键作用域与保留期、何时消费 nonce、相同 HTTP 请求重投是拒绝还是回放，以及 response-lost 后 client 是复用 nonce 还是用新 nonce＋同 mutation ID；也没有规定 secret 的实际存放、双 key 轮换和旧 key 撤销。→ 冻结 wire contract：精确定义 canonical bytes 和常量时间比较；nonce 至少按 `(projectId,keyId,nonce)` 唯一并保留超过最大时钟窗口；传输重试使用新 nonce、稳定 mutation ID，业务层按 canonical payload digest 回放 receipt／拒绝冲突（或者安全缓存完全相同请求的响应，二选一写清）；Lightsail secret 放 root-only secret store，Worker secret 放 Cloudflare Secrets，D1 只存 key metadata；定义 overlap 轮换、撤销和时钟漂移测试。
- [一般] `architecture.md:38,45`：Google transit 的“无换乘”只写成供应商能力，没有说明 adapter 如何验证。Google 的 `routingPreference=FEWER_TRANSFERS` 是偏好而不是“零换乘”保证；若直接信任该请求参数，有换乘路线仍可能进入 20 分钟扩展层。→ `RouteProvider` 必须从返回 legs/steps 规范化总门到门 duration、transit boarding/line identity 与 transfer count；只有总时长 `≤20:00` 且 transit line 不发生切换才标为 direct，步行接驳允许但不能被当成换乘。请求足够的 field mask，对 `20:00/20:01`、一段车＋步行、有换乘、字段缺失和供应商返回偏好不满足分别做 contract fixture。[Google Transit Routes 参数说明](https://developers.google.com/maps/documentation/routes/transit-route)。
- [一般] `architecture.md:45-48,55`：供应商 gate 方向正确，但 Google 与 Leaflet 的可显示数据边界还不够可执行。Google 当前政策限制 Geocoding/Routes 内容缓存，并要求地图展示只能在 Google Map；无 Google Map 展示时需使用清楚、就近且可辨识的“Google Maps” attribution。架构只禁止把“路线”叠到 Leaflet，仍未禁止 Google 派生的地址／坐标／几何进入 Leaflet，也未规定 WeChat 文本中哪些字段组成同一个带 attribution 的内容块；同时 Google 要求应用具备公开 Terms of Use 与 Privacy Policy。→ 在 provider 字段矩阵中逐字段写明 request-only、聊天可显示、可持久化和禁止进入 Leaflet；任何 Google 派生的 geocode/route geometry 均不得在现有 Leaflet/OSM 图层渲染或进入 durable catalog，审计只留非内容标识。回执使用规范“Google Maps” attribution 并与相应内容绑定；上线门增加公开 ToS/Privacy 与 attribution screenshot/text fixture。Foursquare API 字段的持久化权利必须来自实际 API agreement/field evidence，不能只凭同名字段存在于 Places OS schema 推定；rating 继续保持未获书面许可即 unknown。[Google Geocoding policies](https://developers.google.com/maps/documentation/geocoding/policies)、[Google Routes policies](https://developers.google.com/maps/documentation/routes/policies)、[Foursquare response fields](https://docs.foursquare.com/fsq-developers-places/reference/response-fields)。
- [一般] `architecture.md:48,68` 与 `spec.md:173`：只有“供应商日配额、预算告警”不足以验收基础设施、模型、地点发现和路线服务合计月度 run-rate `≤60 美元`；未定义各项预算、调用成本归集、告警阈值或超限降级。尤其 Foursquare 自 2026-06-01 起只有前 500 次 Pro 调用免费，随后为每千次 15 美元，七天 soak 可能轻易改变成本结论。→ 增加可替换的 usage/cost meter：固定成本（Lightsail/Cloudflare）与 DeepSeek、Google、Foursquare 变动成本使用同一月度 projection；为每个 provider 设 warn/hard quota 和总预算 reserve，超限后 provider fail closed 为 unknown／dependency warning，绝不自动升级付费层。Read-only、Write、soak 前各生成可复核的预算报告，并以真实账单/usage counter 校准。[Foursquare 2026 pricing](https://docs.foursquare.com/developer/reference/upcoming-changes)。

## 已通过检查

- 架构明确引用并增量对齐 `product/architecture.md`，保持模块化单体、Ports & Adapters、唯一 `AtlasApplication` 入口、供应商 SDK 位于 adapter 及隔离 Cloudflare PoC 环境。
- canonical `/jpmap` direct-dispatch、capability-gated `PreModelIngressRouter`、每项目 credential/scope/tool/state namespace 及 runtime 变化触发重审的方向与 D-021 一致；待严重 finding 中的跨主机 session lookup 补齐后可形成闭环。
- `EntryAccessSnapshot` 保持 walk-in/queue 两项 assertion、最小持久化与 unknown-first；reservable/open 不推断 walk-in 或 queue，符合规格。
- Cloudflare 前端/API/D1/R2 与 Lightsail runtime 分离，Agent host 可独立迁往 Hetzner/OCI；Product Core 不依赖 Cloudflare SDK，D1/R2 仍位于 ports 后，当前部署没有把私有写入或媒体放入 GitHub Pages/iCloud/Google Drive。
- D1 `batch()` 被用于多语句事务的方向符合当前 Cloudflare contract；问题不在 D1 本身，而在尚未定义覆盖整组 Visit/assessment/media/receipt 的单一应用接缝。
- 当前 Leaflet adapter 已开启 attribution control 并显示 OSM attribution；只要按上述 provider 数据流矩阵禁止 Google 内容进入该地图，就无需为本 PoC 更换地图引擎。

## 结论说明

该架构选定的总体拓扑与供应商 fail-closed 思路合理，但三项严重问题会分别造成 capture 内容误入模型、无法实现规格要求的全组原子可见性，以及明确越过图片隐私边界；另有六项一般问题使 Catalog 深接缝、Agent 工具面、HMAC 重试、直达电车判断、供应商合规和 60 美元成本门尚不可验收。修正这些发现后应进行第 2 轮独立架构复审，当前不得进入 `hf-to-tickets`。
